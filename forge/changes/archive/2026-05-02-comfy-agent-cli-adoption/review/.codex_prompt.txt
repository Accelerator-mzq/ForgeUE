# Context

ForgeUE is a UE production-chain multi-model framework. This change replaces the hand-rolled HTTPComfyWorker (which spoke ComfyUI HTTP /prompt + /history + /view directly and required bundles to inline the entire workflow_graph JSON) with subprocess invocation of the new agent CLI (python invoked via the module flag pointed at the comfyui_api package, documented at D:/AI/ComfyUI/docs/workflows/COMFYUI_AGENT_API.md). The CLI manifest-izes 18 workflows, exposes 4 lifecycle modes, groups outputs by date/project, and standardizes errors. Bundle spec simplifies from inlined workflow_graph to three fields: comfy_workflow + comfy_params + comfy_lifecycle. All ComfyUI-produced files are copied into artifacts/<run_id>/comfy/ to keep the ForgeUE artifact tree self-contained (NFR-PORT-004 + assumption A4).

ForgeUE-side contracts that MUST be preserved: FakeComfyWorker scripted queue (offline test backbone, CI cannot install ComfyUI), three-tier exception hierarchy (WorkerError, WorkerTimeout, WorkerUnsupportedResponse) routed through FailureModeMap, ImageCandidate to PayloadRef.file to ArtifactRepository flow with lineage and hash, executor metrics with cost_usd field (FR-COST-008/009 even though local GPU cost is 0), and WS event emission (worker_poll, step_start, step_done, NFR-OBS-004).

# Adversarial focus

Challenge the design assumptions and surface hidden contract gaps. Specifically interrogate the following Claude self-identified weaknesses (these are documented in review/design_cross_check.md section A Decision Summary, frozen at 2026-05-02 18:10 BEFORE this review):

W-DryRunTimeout: tasks section 3.5 dry-run probe hardcodes a 10s timeout, but Risk A in design.md says ComfyUI cold start is 30 to 90 seconds. Dry-run will false-fail on a cold ComfyUI even though the actual step under lifecycle ensure_running could have started it. Is the 10s probe too strict, or should the probe be skipped at dry-run and only enforced at step time?

W-CopyAsyncBlocking: shutil.copy2 is synchronous IO. ComfyAgentWorker.submit is async. Wrapping the copy directly inside an async submit will block the asyncio event loop, freezing progress event emission for other steps in DAG mode. Does the design need asyncio.to_thread(shutil.copy2, ...) or aiofiles equivalent? The design currently does not say.

W-WindowsCancelKill: design.md Risk C claims Windows terminate is equivalent to POSIX SIGTERM, but in fact Windows asyncio.subprocess.Process.terminate() calls TerminateProcess (a hard kill) while POSIX SIGTERM allows graceful shutdown. When ForgeUE terminates the comfyui_api subprocess, what happens to the ComfyUI server process that comfyui_api itself spawned via lifecycle ensure_running? Is the .comfyui.pid mechanism still able to prevent orphaning the ComfyUI process when the parent CLI is hard-killed?

W-NoModified: All 4 capability spec deltas use ## ADDED Requirements only, none use ## MODIFIED. Inspect openspec/specs/provider-routing/spec.md existing requirements (especially "Capability aliases drive provider selection" which mentions image_fast / image_strong / image_edit). Is there any existing requirement whose behavior implicitly covers ComfyUI such that a MODIFIED delta is needed instead of (or in addition to) ADDED?

W-TasksCheckedTaskApply: tasks.md section 1.2 is marked [x] (completed) because the 3 OQ resolutions were finalized during the design phase. Will /forgeue:change-apply or /opsx:apply skip [x] tasks at apply time? If yes, OQ-3 (--project = task.project_id) gets locked in without re-examination. If no, the [x] is misleading. Design does not document the apply-stage behavior on pre-checked tasks.

W-ManifestNameUndecided: tasks.md section 7.1 hardcodes comfy_workflow value as "GameAssets/01b_singleview_sdxl" for the rewritten examples/comfy_local_smoke.json bundle, but neither design.md, proposal.md, nor any spec explains why this manifest was chosen over alternatives like ComfyUI_Workflows/basic/basic_workflow (the SD1.5 base workflow that v1 inline-graph bundle approximated) or Z_Image/image_z_image_turbo (the Z-Image turbo workflow listed in COMFYUI_AGENT_API.md section 3.2). Is the choice arbitrary, or is there an implicit design rationale that should be surfaced?

W-CancelWrapWorkerExc: D-FailureMap in design.md and the matching spec table list "asyncio.CancelledError propagated to submit()" alongside the worker exception mappings. The expected behavior is to re-raise CancelledError, not wrap it. But putting cancel in the same table as WorkerError/WorkerTimeout/WorkerUnsupportedResponse mappings invites a misread that cancel gets wrapped. Is the table layout misleading enough to warrant restructuring?

W-NfrMaintBaseline: Test total goes from 549 (current acceptance v1.3 baseline) to 549 + 15 new fences - 1 deleted fence = 563. NFR-MAINT-003 floor of 491 (or post-Codex-audit 520) still holds, but the v1.3 acceptance_report explicitly says "实测 549" (measured 549). tasks.md section 9.6 just says "update FR-WORKER-001 acceptance row" but does not explicitly require updating the 549 baseline number. Will doc-sync miss this?

W-DryRunForcedReachability: provider-routing/spec.md adds a requirement "Dry-run pass validates ComfyUI subprocess reachability" that fires "when any step references the image.generation capability via comfy_api". But many bundles use image.generation via Qwen or GLM (image_fast / image_strong aliases), not ComfyUI. Will this requirement trigger the comfyui_api status probe even for runs that never touch ComfyUI? The "via comfy_api" qualifier in the scenario is fuzzy. Should the requirement be tightened to "when prepared_routes actually resolves to a comfy_api provider entry"?

W-ComfyApiAsProviderWithoutModel: config/models.yaml has three sections: providers, models, aliases. The new comfy_api provider entry goes in providers, but ComfyUI does not have a model id concept (the manifest workflow name like GameAssets/01b_singleview_sdxl is more like a recipe than a model id). Does models section need a virtual model id like comfy/local for aliases like image_fast to reference? Or does ComfyUI worker bypass ModelRegistry routing entirely and the bundle just sets capability_ref directly? design.md and the spec deltas do not explain ComfyUI's place in the three-section schema.

# Beyond the self-identified weaknesses

Look for issues Claude missed. Especially check:

- Any conflict with OpenSpec spec convention (MODIFIED vs ADDED used incorrectly; Scenario 4-hashtag rule violations; requirements without scenarios or with misnumbered scenarios).
- Any conflict with existing ForgeUE contracts (SRS, HLD, LLD, acceptance, NFR, ADR-001 through ADR-007, invariants documented in already-archived OpenSpec changes).
- subprocess invocation safety: comfy_params is a dict that comes from user-supplied bundle JSON, then gets json.dumps'd into a CLI argv string. Is there any injection risk (e.g., does comfyui_api parse --params with shlex)? Are pathological values (huge strings, deeply nested dicts) handled?
- shutil.copy2 partial-failure rollback: if copy2 fails halfway through (disk full, permission denied), what state is left? Does the worker need a try/except + cleanup of partial artifacts/<run_id>/comfy/ files?
- Windows-specific edge cases: 260 character path length limit, UNC paths, non-ASCII filenames in outputs.images, file lock contention between comfyui_api writing the PNG and the worker copying it.
- v1 vs v2 ImageCandidate.data byte-equivalence: v1 streamed PNG bytes from /view?filename=X&type=output (HTTP GET); v2 reads from a copied file on disk. Are there any subtle differences (e.g., HTTP server stripping metadata chunks, ImageMagick rewriting EXIF, copy2 preserving vs not preserving Windows ADS) that could break downstream hash equivalence with v1 baselines?
- Migration plan 7-commit chain atomicity: design.md sections lists commit 1 (registry config) -> commit 2 (ComfyAgentWorker rewrite) -> commit 3 (executor reads new fields, raises on legacy workflow_graph) -> commit 4 (FakeComfyWorker schema gate) -> commit 5 (test rewrite) -> commit 6 (examples rewrite) -> commit 7 (docs sync). Does pytest stay green at every intermediate commit? Specifically, after commit 3 the executor rejects workflow_graph but before commit 6 examples/comfy_local_smoke.json still has it (until rewritten in commit 6). Does test_example_bundles_smoke fail between commit 3 and commit 6?
- TBD-009 entry in docs/requirements/SRS.md section 7.3 follows the schema of existing TBD-001 through TBD-005 rows (which all have a "目标决议日期" target resolution date column). The proposed wording "本 change 归档后再评估" (after this change is archived, re-evaluate) is a vague placeholder rather than a date. Does this match the existing TBD row schema, or will it look like a hole?
- v1 inline-workflow snapshot at commit 292420a is referenced by design.md and multiple spec deltas as "comparison baseline" / "preserved in git history". This commit is on branch chore/openspec-superpowers, but if the branch is ever rebased / squashed before merge, commit 292420a may be rewritten or lost. Does the design rely on this commit hash being permanent? Should the v1 files instead be moved to docs/archive/ for a hash-independent reference?
